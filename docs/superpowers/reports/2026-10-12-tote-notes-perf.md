**배경에서 잴 수 있는 시나리오는 전부 「된다」다. 파일 열기 5개는 화면 측정(Task 17)에서도 전부 「된다」이고, 세션 복원은 화면 측정 값이 규칙상 「안 된다」이지만 화면 잠김으로 보류했다.** 배경 측정에는 「조건부」·「안 된다」가 없다. 파일 열기와 세션 복원은 지표의 끝 마크가 애니메이션 프레임(rAF)에 찍히는데, 사람의 화면을 쓰지 않으려고 띄운 배경 창(`TOTE_BACKGROUND=1`)에서는 rAF 가 믿을 수 없게 돈다 — 그래서 판정하지 않고 화면 측정으로 넘긴다(아래 「실측 불가」).

## 환경

- 기기 Mac17,9 · Apple M5 Pro · 48GB, macOS 27.0.1 (26A434), 전원 연결(AC).
- **디스플레이: 규칙(내장 디스플레이)과 다르다.** 켜진 디스플레이는 2560×1440 외장 두 대(주 디스플레이 하나)다. 배경 창은 화면에 합성되지 않으므로 이번 시나리오의 값에는 디스플레이가 끼지 않는다고 보지만, 화면 측정(Task 17)은 내장 디스플레이로 쟀다.
- 빌드: `perf` 프로필(`src-tauri/Cargo.toml` — `inherits = "release"`, tote 크레이트만 `debug-assertions = true`, 의존 크레이트는 끔), `tauri.dev.conf.json`(식별자 `dev.tote.note.dev`), 번들 `src-tauri/target/perf/bundle/macos/tote-dev.app`.
- 앱은 `TOTE_DATA_DIR=<mktemp -d>`·`TOTE_PERF=1`·`TOTE_BACKGROUND=1` 로 띄웠다. 측정 뒤 `~/Tote-dev`·`~/Library/Application Support/tote-dev` 는 생기지 않았다.
- 부하: 시작 전 1분 load average 가 3.37 이라 규칙대로 기다렸다가 2.20 에서 시작했다. 시나리오마다 시작 때 값은 1.19–2.27(`tests/measure/results/load.txt`). 같은 기기에서 다른 에이전트 세션들이 돌고 있었다(주로 `ccstatusline` 프로세스) — 「측정 중 다른 작업 없음」은 이 워커의 작업 기준이다.
- 픽스처: `pnpm perf:fixtures /tmp/tote-perf-fixtures`. `code-100mb.ts` 는 104,857,627바이트로 편집기 상한(100MiB)을 넘어 대용량 텍스트 뷰어로 간다.

## 규칙

`tests/measure/perf.md` 가 사본이다(정본은 계획 「Task 16: 성능 계측과 목표치」). 측정 전에 사전 점검 판정과 코디네이터 판정으로 더한 것은 그 파일 「측정 전에 더한 것」 절에 있다 — 의존 크레이트의 `debug-assertions`(M11), `tote <파일>` 호출 경로(M10), 세션 파일 이름(L13 ①), 콜드 스타트의 출발점이 `main` 진입이라는 정의(L13 ②), 배경 창의 rAF, 감시 배치 비용의 지표. 목표·판정 규칙은 바꾸지 않았다.

읽을 때 알아 둘 것:

- **검색 1회차 416.2ms** 는 측정 폴더를 복사한 직후 첫 실행이다(준비 실행 한 번 뒤). 2–5회차는 165–176ms 로 모인다. 규칙이 중앙값으로 판정하므로 판정에는 영향이 없다.
- **검색은 창이 막 선 직후에 돈다.** `TOTE_PERF_SEARCH` 분기는 `start()` 끝(`app-ready` 직후)에 검색을 띄우므로, 메모 1만 개 목록 그리기·마크다운 문법 미리 읽기와 겹친다. 사람이 창을 띄워 두고 검색하는 경우보다 불리한 쪽이다.
- **첫 색칠은 배경 창에서 쟀다.** 토큰은 rAF 가 아니라 타이머·워커로 오므로 마크는 찍히지만, 편집기가 rAF 로 화면 범위를 재지 못했을 수 있어 「첫 화면 범위」가 추정 범위일 수 있다. 화면 측정 때 같은 회에서 다시 나오므로 그때 함께 확인한다.
- **메모리는 tote 프로세스 하나의 RSS 다.** WKWebView 의 WebContent 프로세스는 따로라 들어 있지 않다. 「뷰어로 연 뒤 10초」의 출발점은 배경에서 `open-first-paint` 를 믿을 수 없어 `open-start` 로 잡았다.
- **감시 배치**는 한 회 = 창이 선 뒤 메모 하나를 tote 의 저장처럼(같은 폴더의 `.tote-tmp-*` 에 쓰고 rename) 바꾸고 2초 동안 온 배치의 처리 시간 합이다. 배치는 워크스페이스 잠금을 쥔 채 폴더를 `read_dir` 하므로(`Workspace::apply_fs_events`) 그 시간만큼 같은 워크스페이스의 저장이 기다린다. 메모 1만 개에서 중앙값 4.9ms·최대 12.1ms, 50개에서 0.2ms 다.

## 실측 불가 — 배경 창의 rAF

`TOTE_BACKGROUND=1` 창은 화면에 올라오지 않고, WKWebView 는 그 창의 `requestAnimationFrame` 을 믿을 수 없게 돌린다. 파이프라인 스모크(시나리오가 아닌 `code-1mb.ts` 1회)에서 `open-first-paint` 가 60초 동안 오지 않아 코디네이터 판정(A)으로 **파일 열기 5개와 세션 복원을 「실측 불가 → 화면 측정」**으로 넘겼다. 마크 정의·목표는 그대로다.

그 뒤에 본 것(판정에 쓰지 않는다 — 화면 측정으로 확정해야 한다):

- **세션 복원을 배경으로 5회 재 봤다(코디네이터 판정 A2).** 1회차는 60초 안에 `restore-done` 이 없어 무효, 2회차 **53,385.2ms**(rAF 가 53초 동안 멈췄다), 3–5회차 346.4·322.9·316.7ms. 규칙상 무효가 하나라 재실행은 아니고 중앙값은 334.7ms 로 계산되지만, 2회차 값이 rAF 정지를 잰 것이라 **판정하지 않는다.** 프레임을 받은 회의 복원은 300ms 대다.
- 배경 열기 회차의 `perf.jsonl` 에 `open-first-paint` 가 찍힌 회도 있다(토큰이나 메모리를 기다리는 동안 우연히 받은 것): `code-10mb.ts` 67.3·84.0·67.5ms(3/5), `code-10mb.md` 105.3·132.9ms(2/5), `code-100mb.ts` 77.7·128.0·120.9·122.7ms(4/5). 찍힌 값은 목표(500ms·1,000ms) 안쪽이지만 나머지 회는 프레임이 안 와서 빠진 것이라 표본이 고르지 않다.
- 같은 이유로 `restore-done` 은 세션이 없는 창에서 `app-ready` 직후 약 10ms 에 찍히곤 한다 — 창이 막 뜬 동안은 프레임을 받고, 몇 초 뒤에는 멈추는 것으로 보인다.

- 첫 열기 `code-10mb.ts` 1회차 175.9ms 는 나머지(약 70ms)의 두 배 반이다. 중앙값에는 영향이 없다. 위 「배경」 첫 색칠 값(125.9·158.4ms)과 이번 화면 값(127.6·159.6ms)이 같은 수준이라 첫 색칠 지표는 배경에서 잰 값도 믿을 만했다.

- 위 열기 시나리오는 시나리오 사이 로드가 높을 때 스크립트가 멈춰 기다린 것(`load 13.67 >= 3, waiting`)과 `restore-50` 이전에 모두 끝났다. 열기 5개의 마크는 전부 있고 무효는 0 이다.
- 이 화면 측정 중 `tests/measure/results/` 의 `open-*`·`restore-50` 파일과 `summary.md` 는 위 값으로 덮어쓰였다(그 디렉터리는 git 에 없다). 배경 값은 이 문서의 「결과 — 시나리오별 5회」 표에 남아 있다.

### 화면 측정 명령(사람 동의 뒤)

창이 화면에 올라오고 포커스를 가져간다. 약 15분, 앱이 약 40번 떴다 꺼진다. 내장 디스플레이에서, 다른 작업 없이 돌린다.

```bash
pnpm perf:fixtures /tmp/tote-perf-fixtures
TOTE_DATA_DIR=$(mktemp -d) PERF_FOREGROUND=1 \
  PERF_ONLY="open-ts-10mb open-md-10mb open-ts-100mb open-json-10mb open-log-100k restore-50" \
  pnpm perf:measure /tmp/tote-perf-fixtures
```

`PERF_FOREGROUND=1` 은 `TOTE_BACKGROUND` 를 빼고(`TOTE_DATA_DIR` 은 그대로) 집계에서 프레임 시나리오를 판정 대상에 넣는다. 끝나면 `tests/measure/results/summary.md` 에 표가 나온다.

## 사람에게 올릴 것

- **세션 복원 탭 50개의 판정** — 규칙상 「안 된다」(중앙값 46,016.7ms)이지만 화면 잠김으로 보류한다 — 화면이 켜진 상태에서 다시 재서 사람이 판정한다. 화면 측정 중 세션이 잠겨 5회 중 2회만 정상 프레임을 받았다. 화면이 잠기지 않은 상태에서 `PERF_FOREGROUND=1 PERF_ONLY=restore-50` 로 다시 재야 한다. 파일 열기 5개는 화면 측정으로 판정을 마쳤다(전부 「된다」).
- **메모리 117MB(tote 프로세스, 100MB 파일을 뷰어로 연 뒤)** — 목표가 없어 기록만 했다. WebContent 프로세스는 빠져 있다. 목표를 둘지 정해야 한다.
- **감시 배치 비용** — 메모 1만 개에서 저장 하나당 배치가 잠금을 4.9ms(최대 12.1ms) 쥔다. 사람이 느낄 저장 지연은 아니라고 보지만, 판정 기준이 없어 기록만 했다.
- **디스플레이 조건** — 이번 측정은 외장 디스플레이 환경이었다. 배경 시나리오에는 영향이 없다고 보지만 규칙과 다르다.

## 재지 않은 것

규칙 「재지 않는 것」대로 키 입력 지연(아래 긴 줄 재실행만), 스크롤 프레임(계측 지점 없음), Zed·Sublime 과의 수동 비교, 한글 조합 키 지연은 재지 않았다. 재부팅 콜드 스타트도 재지 않았다.

## `pnpm measure:long-line` 재실행

규칙 「재지 않는 것」대로 하이라이트 변경(Task 15) 뒤 같은 절차를 한 번 다시 돌려 `LONG_LINE_LIMIT` 판정이 바뀌는지만 봤다. **판정은 그대로 200,000 이다** — `code.ts` 경계 5,000,000(8단계 전부 「된다」), `note.md` 경계 200,000(500,000 부터 두 실행 모두 「안 된다」), 작은 값 200,000. 값은 바꾸지 않았다.

- 두 형식·두 실행 모두 유효: T(rAF 간격 중앙값) = 13ms(8–20ms 안), 기준선 p95 5–7ms(≤ 3T). headless WebKit, 이 측정과 같은 기기.
- 경계 바로 위·아래의 `note.md` p95 − 기준선: 200,000 은 5.0·6.0ms(≤ T), 500,000 은 15.0·16.0ms(> T). 직전 측정(`docs/superpowers/reports/2026-10-11-long-line-boundary.md`)의 6·7ms, 18·19ms 와 같은 쪽에 선다.
- 이 절차는 편집기 단독 페이지(하이라이트 워커 없음)에서 재므로 Task 15 의 워커 변경을 직접 건드리지 않는다. 판정이 안 바뀐 것은 그 점과도 맞는다.
- 회별 표 전체는 `pnpm measure:long-line` 의 출력과 `tests/measure/results/long-line.json` 에 나온다.

## 다시 재는 법

```bash
pnpm perf:fixtures /tmp/tote-perf-fixtures          # 픽스처
TOTE_DATA_DIR=$(mktemp -d) pnpm perf:measure /tmp/tote-perf-fixtures   # 빌드 + 배경 측정 + 표
node scripts/perf-summary.ts tests/measure/results   # 모은 회로 표만 다시
```

`PERF_SKIP_BUILD=1` 은 번들을 다시 쓰고, `PERF_ONLY="<시나리오…>"` 는 그것만 잰다. `PERF_BACKGROUND_RESTORE=1` 은 세션 복원을 배경으로도 돌린다(위 관찰값을 낸 방법 — 판정용이 아니다). 시작 전에 `tote-dev` 가 떠 있으면 멈추고, 1분 load average 가 3 이상이면 기다린다.
