# 긴 줄 경계 실측 — `LONG_LINE_LIMIT`

이 문서는 그 시점의 기록이다. 값을 다시 정하려면 `pnpm measure:long-line` 을 돌린다.

## 결과

**`LONG_LINE_LIMIT = 200_000`** — `code.ts` 의 경계 5,000,000 과 `note.md` 의 경계 200,000 중 작은 값. 첫 측정(`code.ts` 만, 5,000,000)은 리뷰에서 `note.md` 를 덮지 못한다고 지적돼 폐기하고 다시 쟀다(아래 「경위」).

## 환경

- macOS 27.0.1, Apple M5 Pro, Playwright WebKit(headless), `Desktop Safari` 프로파일. rAF 간격 중앙값 17ms(≈ 60Hz).
- 편집기 단독 페이지(`tests/e2e/pages/editor.html`, 하이라이트 없음)에서 영문을 쳤다. 줄바꿈은 앱의 규칙(`longestLine <= WRAP_LIMIT`)대로 정해지므로 사다리 값(모두 20,000 이상)에서는 꺼져 있다.

## 사전 등록 규칙(데이터를 보기 전에 고정한 것)

- 사다리: 20,000 · 50,000 · 100,000 · 200,000 · 500,000 · 1,000,000 · 2,000,000 · 5,000,000 자(한 줄). 기준선은 253줄 코드(각 줄 `const v<i> = f(<i>) + "text";`).
- 지표: 키 입력 지연. 조합마다 영문 60타, 문서가 바뀐 키만 센다. p95. T = 같은 실행에서 잰 rAF 간격 중앙값(120 프레임).
- 판정: 조합 p95 − 기준선 p95 ≤ T 면 「된다」. 경계 = 두 실행 모두 「된다」인 가장 큰 사다리 값(보간 없음, 안 되는 값을 만나면 거기서 멈춘다).
- 유효성: 기준선 p95 > 3T 이거나 T 가 8–20ms 밖이면 그 실행은 무효. 무효가 둘 연속이면 headed, 그래도 무효면 「실측 불가」 + 잠정값 1,000,000.
- 적용: 20,000 조차 안 되면 20,000.
- 측정 전에 스크립트를 규칙에 맞춘 곳(사전 점검 F41·F42): 유효·무통과면 `null` 대신 20,000, 측정 페이지의 줄바꿈을 앱의 규칙으로.

## 경위 — 규칙 밖에서 정한 것(측정 대상 파일 형식)

규칙은 측정 대상 파일 형식을 정하지 않았다. 첫 측정은 `code.ts`(파서 없음)만 재서 5,000,000 이 나왔다. 리뷰어가 1회 탐침으로 `note.md`(Lezer 마크다운이 붙는 메모의 기본 형식)가 1,000,000자부터 판정선을 넘는 것을 보였고, **그 탐침을 본 뒤에** 코디네이터가 판정했다: `LONG_LINE_LIMIT` 는 모든 형식에 하나로 적용되므로 `code.ts` 와 `note.md` 를 각각 사전 등록 절차(두 실행)로 재고 **작은 값**을 쓴다. 사다리·지표·판정·유효성은 바꾸지 않았다.

다시 잴 때 바꾼 측정 방식(결과를 보기 전에 고정): ① 끝점을 스파이크(`spikes/lab/src/perf/latency-page.ts`)와 같게 — 시작은 keydown 의 `e.timeStamp`(CodeMirror 보다 먼저 받도록 capture), 끝은 rAF 뒤 `setTimeout(0)`. ② `End` 뒤 500ms 기다려 그 rAF 가 첫 글자에 섞이지 않게 해 키 수가 60 이 되게. ③ 키별 지연 배열을 남김.

## 검증하지 않은 것

- **headless WebKit 의 수치다.** 실제 앱(WKWebView)과 엔진은 같지만 창·합성 경로가 달라 절대값이 같다고 보장하지 못한다. 스파이크의 `json-10mb-one-line`(WKWebView, `basicSetup`, JSON 내용, p95 +34ms)은 이 측정이 재현도 반박도 하지 못한다 — 내용이 `"x"` 반복이고 JSON 파서 언어를 재지 않았다.
- 재지 않은 형식: 언어 파서가 붙는 다른 확장(코드 하이라이트 Worker 가 꺼진 상태라 JSON·YAML 등), 한글 조합 입력, 줄 가운데 편집·선택·스크롤·찾기, 열기 시간·메모리.
- 재지 않은 수준: 사다리 위(5,000,000 초과).
- **기준선 rAF 위상 잡음.** headless WebKit 의 rAF 위상 때문에 같은 기준선 p95 가 실행마다 한 프레임만큼(2ms ↔ 16ms) 흔들릴 수 있다. 이번 기준선은 네 번 모두 3–4ms 였으나, 위상이 달라지면 같은 대상의 판정선이 한 프레임 만큼 오르내린다.
- 하이라이트 Worker 없이 쟀다(20,000자를 넘는 줄은 하이라이트 가드로 어차피 색이 없다).
