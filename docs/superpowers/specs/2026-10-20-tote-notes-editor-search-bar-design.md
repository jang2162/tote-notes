# tote-notes 편집기 검색 띠(⌘F) — 설계

2026-10-20. 사용자 요청: 「⌘F 시 UI 개선」. 사용자가 짚은 것은 둘이다 — 「다크모드에서 색대비 안 맞음」, 「기능에 맞게 일렬로 버튼·입력필드를 배치한 느낌이라 직관적이지 않음」. 시안 두 가지(오른쪽 위에 떠 있는 상자, 위쪽 띠) 가운데 사용자가 **위쪽 띠(Zed 식)** 를 골랐다. 아래 「동작」 과 「하지 않는 것」 은 설계자가 정리해 사용자에게 보였고 사용자가 「진행해줘」 로 받았다. 그 밖에 이 문서에서 정한 것은 **설계자 판단**으로 표시한다.

## 왜

지금 ⌘F 는 CodeMirror 기본 검색 패널(`search({ top: true })`, `src/editor/setup.ts`)을 그대로 띄운다.

- 입력칸·버튼이 브라우저 기본 모양이라 다크 테마에서 흰 입력칸·밝은 그라데이션 버튼이 뜨고, 글자 대비가 맞지 않는다. 패널 배경만 `--panel-bg` 로 칠해져 있다.
- 찾기 입력칸, next·previous·all, 체크박스 셋(match case·regexp·by word), 바꾸기 입력칸, replace·replace all, × 가 한 줄에 흘러가듯 늘어선다. 무엇이 찾기이고 무엇이 바꾸기인지, 옵션이 어느 입력칸에 걸리는지 모양으로 드러나지 않는다.
- 문구가 영어다. 결과가 몇 개인지, 지금 몇 번째인지 보이지 않는다.

## 목표

1. ⌘F 를 누르면 **그 칸 맨 위에 얇은 띠**가 붙고 글은 아래로 밀린다. 띠는 찾기 줄과, 평소에는 접혀 있는 바꾸기 줄 두 줄로 된다.
2. 띠의 모든 요소가 앱 테마 색을 따르고, **다크·라이트 둘 다 글자 대비가 4.5:1 이상**이다.
3. 지금 몇 번째 결과인지와 전체 개수(「3 / 12」)가 보인다.
4. 문구가 한국어다.

## 하지 않는 것

- 워크스페이스 검색(⇧⌘F, 사이드바 검색 패널).
- 대용량 뷰어(`src/viewer/large-text.ts`)의 검색칸.
- 여러 파일에 걸친 바꾸기, 검색 기록(이전 검색어 목록), 선택 영역 안에서만 찾기.
- 편집기 단축키 바꾸기 기능(편집기 키는 지금처럼 고정).

## 하면 실패인 것

- 다크 테마에서 흰 입력칸이나 대비가 4.5:1 에 못 미치는 글자가 남는다.
- 한글 조합 중 Enter 가 다음 결과로 넘어가 버린다(조합 확정 Enter 를 검색 이동으로 먹음).
- 모두 바꾸기가 ⌘Z 한 번에 되돌아오지 않는다.
- 띠를 닫았는데 편집기에 포커스가 돌아오지 않는다.
- 탭을 바꾸거나 칸을 나눴을 때 다른 칸에 띠가 따라가거나, 한 칸의 띠 상태가 다른 칸에 섞인다.
- 결과가 아주 많은 메모(수만 개), 또는 결과가 적은 큰 메모(수 MB)에서 띠를 연 채 타이핑·커서 이동이 개수 세기 때문에 끊긴다.

## 모양

```
┌──────────────────────────────────────────────────────────────────┐
│ [ my                         Aa  ab  .* ]  3 / 12   ↑  ↓  ⇄  ×   │  찾기 줄
│ [ 바꿀 내용                             ]  [바꾸기] [모두 바꾸기]  │  바꾸기 줄(접힘이 기본)
└──────────────────────────────────────────────────────────────────┘
  1 │ 오늘 할 일
  2 │ - my notes 정리
```

- **찾기 줄:** 넓은 입력칸(남는 폭을 다 씀) 안 오른쪽에 옵션 토글 셋 — `Aa` 대소문자 구분, `ab` 단어 단위, `.*` 정규식. 입력칸 밖에 개수 표시, 이전(↑)·다음(↓), 바꾸기 줄 펼치기(⇄), 닫기(×).
- **바꾸기 줄:** 「바꿀 내용」 입력칸(찾기 입력칸과 같은 폭으로 정렬), 「바꾸기」, 「모두 바꾸기」. ⇄ 가 켜져 있을 때만 보인다.
- 옵션 토글과 아이콘 버튼은 눌린 상태가 모양으로 드러난다(켜짐: 강조색 옅은 바탕 + 강조색 테두리). 각각 `title` 과 `aria-label`(「대소문자 구분」, 「단어 단위」, 「정규식」, 「이전 결과」, 「다음 결과」, 「바꾸기 펼치기」, 「닫기」)과 `aria-pressed` 를 갖는다.
- 개수 표시는 결과가 있으면 「3 / 12」, 커서가 결과 위에 있지 않으면 「– / 12」(설계자 판단), 입력이 비었으면 비움, 결과가 없으면 「결과 없음」. 숫자는 고정폭 숫자(`tabular-nums`)로 폭이 흔들리지 않게 한다.
- 정규식이 틀리면 입력칸 테두리를 `--danger` 로 칠하고 개수 자리에 「잘못된 정규식」 을 보인다.
- 크기는 사용자가 고른 시안(저장소 밖이라 수치를 여기 옮긴다)을 따른다: 띠 안쪽 여백 위아래 6px·좌우 10px, 두 줄 사이 6px, 입력칸 높이 26px·모서리 6px·왼쪽 안쪽 8px, 옵션 토글 22×20px(모서리 4px), 아이콘 버튼 24×24px(모서리 5px), 글자 버튼 높이 24px·좌우 10px, 개수 표시 최소 폭 52px·12px 글자, 요소 사이 4px.
- 입력칸 글꼴은 앱 UI 글꼴이 아니라 **편집기 글꼴**(`--editor-font`)을 쓰되, 글자 크기는 편집기 크기를 따르지 않고 **13px 고정**이다(설계자 판단: 찾는 글자와 메모 속 글자가 같은 모양이어야 공백·기호를 알아보기 쉽고, 크기를 고정해야 편집기 글꼴을 24px 로 키워도 띠가 한 줄 인상을 지킨다).

## 색

- **클래스 이름:** 띠의 CSS 클래스 접두사는 `find-bar` 이다(`.find-bar`, `.find-bar-find` 등). 사이드바 워크스페이스 검색이 `.search-bar` 를 이미 쓰므로 겹치지 않게 했다.
- 띠 배경 `--panel-bg`, 아래 경계 `--border`. 입력칸 배경은 편집기 배경(`--bg`)보다 한 단계 어둡게/밝게 새 변수 `--input-bg` 로 둔다(설계자 판단. 라이트·다크 기본값을 `src/styles.css` 와 `src/theme/vscode-theme.ts` 의 `DEFAULT_VARIABLES` 양쪽에 같은 값으로 넣고, VS Code 테마의 `input.background` 를 이 변수에 잇는다).
- 테마가 이 변수들을 주지 않으면 그 테마 **종류**(라이트·다크)의 기본값이 들어간다. 슬롯(OS 모양)의 기본값이 아니다 — 다크 슬롯에 Light+ 를 고르면 띠는 라이트 기본값이다(코어 설계 「테마」, 스모크 A-4).
- 입력칸 글자 `--fg`, 자리표시 글자 `--muted`, 포커스 테두리 `--accent`.
- 결과 칠: 나머지 결과는 옅은 노랑(`--search-match`), 지금 결과는 진한 주황 바탕 + 주황 테두리(`--search-match-current`). 새 변수 둘을 위와 같은 방식으로 두고 VS Code 테마의 `editor.findMatchHighlightBackground`·`editor.findMatchBackground`(+`editor.findMatchBorder`)에 잇는다. 칠한 위에서도 글자가 읽혀야 한다(바탕은 반투명).
- **대비 기준:** 띠의 모든 글자(입력칸 글자, 자리표시, 개수 표시, 버튼 글자, 「결과 없음」·「잘못된 정규식」)가 자기 바탕 위에서 4.5:1 이상, 아이콘·토글 테두리는 3:1 이상. 다크·라이트 기본 테마 둘 다. 이 기준을 맞추려고 라이트 `--muted` 를 `#6e7781` 에서 `#656d76` 으로 진하게 했다(앱 전체 보조 글자에 적용된다). 지난 계획처럼 값으로 계산해 시험으로 고정한다.

## 동작

- **열기:** ⌘F 는 찾기 줄만 연다. 편집기에서 글을 고른 채(한 줄 안) 누르면 그 글이 찾기 입력칸에 들어가고 전체가 선택된다. 고른 글이 없으면 그 칸의 직전 검색어가 남아 있고 전체가 선택된다. 이미 열려 있으면 입력칸으로 포커스만 옮기고 전체를 선택한다.
- **⌥⌘F:** 바꾸기 줄까지 펼쳐서 연다(편집기 keymap 에 추가. ⌘F·⌥⌘F 둘 다 scope 를 `editor search-panel` 로 걸어, 찾기·바꾸기 입력칸에 포커스가 있을 때도 먹는다. 단축키 설정 화면의 「편집기(고정)」 목록과 충돌 검사는 keymap 에서 꺼내 쓰므로 자동으로 따라온다 — `editorBindings`, `src/shortcuts/keys.ts`). 앱 메뉴 기본 단축키와 CodeMirror 기본 keymap 에는 ⌥⌘F 가 없음을 설계 때 확인했다. 사용자가 단축키 설정에서 앱 명령에 ⌥⌘F 를 걸면 지금 규칙대로 「편집기 키를 가린다」 경고가 뜨고 메뉴가 이긴다 — 그때 바꾸기 줄은 ⇄ 로 연다. ⌘F 는 keymap 에 두 번(띠의 `openSearchBar`, CodeMirror 기본 `openSearchPanel`) 나오지만 충돌 경고는 첫 것만 쓰므로 「편집기의 openSearchBar 을 가립니다」 가 된다.
- **키:** 찾기 입력칸에서 Enter 다음, ⇧Enter 이전. 바꾸기 입력칸에서 Enter 는 「바꾸기」, ⌘Enter 는 「모두 바꾸기」(설계자 판단, VS Code 와 같음). Esc 는 띠를 닫는다. ⌘G·⇧⌘G(다음·이전)와 F3 은 띠가 열려 있든 아니든 지금처럼 동작한다. **한글 조합 중(`isComposing`)의 Enter 는 조합 확정에만 쓰고 이동하지 않는다.**
- **입력하는 대로 찾기:** 입력이 바뀌면 바로 결과를 다시 칠하고 개수를 다시 센다. 커서 뒤 가장 가까운 결과로 이동하지는 않는다(CodeMirror 기본과 같음 — 설계자 판단: 입력 중 화면이 튀지 않게). Enter 를 눌러야 이동한다.
- **개수 세기:** 결과를 앞에서부터 세되 **1000 개에서 멈추고 「1000+」** 로 보인다(설계자 판단). 지금 몇 번째인지는 지금 선택 위치가 결과와 같을 때만 센다. 지금 결과가 앞 1000 개 안이면 「17 / 1000+」, 그 뒤면 「– / 1000+」. 상한은 표시에만 걸리고 이동·모두 바꾸기는 모든 결과에 걸린다.
  - **시간 예산:** 한 번 세기가 약 30ms 를 넘기면 거기서 멈추고 찾은 개수 n 으로 「n+」 를 보인다(「1000+」 와 같은 꼴 — 「적어도 n 개」). 결과가 없는 긴 구간에서도 멈추도록 줄 끝에서 끊은 조각(약 64K 글자)마다 시계를 본다. 줄을 넘을 수 있는 검색어(리터럴의 줄바꿈, CodeMirror 가 여러 줄로 찾는 정규식)는 한 조각으로 찾으므로 결과 사이에서만 멈춘다. 예산으로 멈췄을 때 지금 결과는 찾은 범위 안이면 번호, 아니면 「–」.
  - **「n+」 는 이어 세기 동안의 중간값이다:** 예산으로 멈춘 세기는 다음 차례(`setTimeout(…, 0)` 한 번씩)에 멈춘 자리부터 다시 30ms 씩 이어 세어, 끝까지 세면 정확한 「k / N」, 1000 개에 닿으면 「1000+」 가 된다. 멈춘 자리는 마지막 결과의 끝(빈 결과면 그 다음 글자, CodeMirror 커서가 스스로 이어 갈 자리), 결과 없이 조각 사이에서 멈췄으면 다음 조각의 처음이다. 이어 세는 중에 문서·검색어가 바뀌거나 띠가 닫히면 이어 세기를 버린다 — 옛 위치로 잇지 않고 위의 규칙대로 처음부터 다시 센다. 이어 세는 동안 찾은 것이 0 이면, 직전 표시가 **같은 검색어(검색 글자·대소문자·정규식·단어 옵션)의 것일 때만** 그대로 둔다(「결과 없음」 과 「– / 0+」 를 오가지 않게). 검색어가 바뀐 뒤의 첫 표시는 직전 검색어의 개수나 「잘못된 정규식」 을 물려받지 않고 「– / 0+」 를 보인다. 바꿈 글자만 바꾸면 결과가 같으므로 다시 세지 않는다. 줄을 넘는 정규식이 줄 머리(`^`)·단어 경계·뒤돌아보기처럼 앞 글자에 기대면, 이어 센 자리에서는 CodeMirror 커서가 앞 글자를 보지 못해 이어 센 개수가 한 번에 센 수와 하나쯤 다를 수 있다. CodeMirror 의 다음 찾기도 같은 방식으로 찾으므로 고치지 않는다.
  - **선택만 바뀌면 다시 세지 않는다:** 문서·검색어가 그대로면 마지막으로 센 결과 위치 목록(최대 1000 개 + 상한 여부)에서 지금 결과만 이진 탐색으로 다시 찾는다.
  - **문서가 바뀐 다시 세기는 미룬다:** 마지막 변경 뒤 150ms 쉬면 센다. 그 사이 개수 표시는 옛 값 그대로다. 검색어·옵션이 바뀐 다시 세기는 다음 프레임에 한다.
- **바꾸기:** 「바꾸기」 는 지금 결과를 바꾸고 다음 결과로 간다. 「모두 바꾸기」 는 한 트랜잭션이라 ⌘Z 한 번에 되돌아온다. 이 앱의 ⌘Z 는 `undoWithCursors`(`src/editor/ime.ts`)이므로 그것으로 확인한다. 한 번에 안 되돌아오면 고치는 것까지 이번 범위다. 정규식 켜짐이면 `$1` 같은 참조가 먹는다(CodeMirror 기본).
- **메뉴 되돌리기:** 편집 › 실행 취소·실행 복귀도 ⌘Z 키와 같다. 이 두 항목은 시스템 항목이 아니라 앱 항목이다(`src-tauri/src/app/menu.rs`). 시스템 항목은 WebKit 의 되돌리기 기록을 거슬러 가는데, 그 기록에는 브라우저가 직접 편집한 것(입력칸과 편집기의 글자 타이핑)만 있고 CodeMirror 가 낸 트랜잭션(모두 바꾸기, 붙여넣기, Enter 등)은 없다. 그래서 모두 바꾸기 뒤 편집기에서 메뉴 Undo 를 누르면 본문 대신 바꾸기 입력칸의 타이핑이 되돌려졌다(검색 띠 스모크 B-5). 이제 페이지가 받아(`src/editor/history-menu.ts`) 무엇에 포커스가 있는지로 고른다.
  - 편집기에 포커스가 있으면 그 편집기의 기록(`undoWithCursors`·`redoWithCursors`). 포커스가 페이지나 칸 자체에 있으면 그 칸의 편집기(편집기를 보이고 있을 때).
  - 입력칸(찾기·바꾸기, 사이드바·대화상자의 입력칸)이나 뷰어 프레임에 포커스가 있으면 WebKit 의 되돌리기(`document.execCommand`)로 그 입력을 되돌린다. 사이드바·대화상자의 다른 요소에 포커스가 있을 때도 WebKit 의 것이다. WebKit 의 기록은 창 하나에 하나라서, 맨 위 칸이 다른 칸의 입력칸 것이면 그 입력칸이 되돌려지고 포커스가 그리로 간다(시스템 항목과 같다).
  - WebKit 의 기록은 창 하나에 하나라서, 입력칸에서 되돌리다 보면 그 아래 칸인 편집기 타이핑에 닿는다. 그 `beforeinput`(`historyUndo`·`historyRedo`)은 포커스가 없는 편집기로 가는데, 편집기는 그것을 버린다(`historyStaysWithTheKeys`). 입력칸의 되돌리기가 메모 본문을 바꾸지 않게 하는 것이다(스모크 B-2 의 기대). 버린 칸도 WebKit 기록에서는 빠지므로, 입력칸에서 그만큼 더 눌러도 아무것도 바뀌지 않는다.
  - tote 창이 아니라 다른 창(파일 고르기 시트 등)이 키를 갖고 있으면 그 창에 시스템 동작(`undo:`·`redo:`)을 보낸다. 앱 모달 패널이 떠 있는 동안 앱 항목이 눌리는지는 화면 확인 전이다.
  - 메뉴 항목은 되돌릴 것이 없어도 켜져 있다(시스템 항목은 WebKit 기록이 비면 꺼졌다). 이름은 「실행 취소」·「실행 복귀」 다(시스템 항목은 영어였다).
- **닫기:** × 또는 Esc 로 닫으면 편집기로 포커스가 돌아가고, 지금 결과가 선택된 채로 남는다.
- **칸·탭:** 띠는 칸마다 따로 열린다(CodeMirror 패널이 그 칸의 `EditorView` 에 붙는다). 띠 열림·검색어·옵션·바꾸기 펼침은 **탭(EditorState)마다** 따로 기억한다(설계자 판단). 앞의 셋은 CodeMirror 검색 상태가 state 에 있으므로 그대로 따르고, 바꾸기 펼침은 작은 StateField 하나로 같은 state 에 둔다. 탭을 바꾸면 그 탭의 상태대로 띠가 열리거나 닫히고 펼침도 따라온다. 탭을 바꾸면 띠 DOM 이 다시 만들어지므로 입력칸 포커스는 이어지지 않는다(포커스는 지금처럼 편집기로 간다).
- **파일 다시 읽기:** 바깥에서 파일이 바뀌어 탭이 새 state 로 다시 만들어질 때(`reload`·`setText`, `src/app/docs.ts`) 띠가 열려 있었다면 검색어·옵션·펼침을 새 state 로 옮겨 띠를 연 채로 둔다(설계자 판단: 검색하던 중 파일이 바뀌었다고 띠가 사라지면 하던 일을 잃는다). 입력칸 포커스는 보장하지 않는다. 다시 만들어진 띠는 포커스를 가져가지 않는다 — 다른 칸에서 치던 글자는 그 칸에 그대로 들어간다(띠 입력칸은 그 칸의 편집기에 포커스가 있을 때, 곧 ⌘F·⌥⌘F 로 열 때만 포커스를 잡는다. 최종 리뷰 I1). 띠를 옮기는 일은 CodeMirror 가 밖에 내놓지 않는 패널 열기 효과에 기대므로, 라이브러리를 갱신해 그 효과를 얻지 못하게 되면 **조용히 닫힘으로 떨어진다**(띠가 닫힌 채 새 state 가 되고 다시 읽기 자체는 그대로 끝난다). 이 대체 동작은 단위 시험(`src/editor/search-bar.test.ts`)이 알린다.

## 구현 방향 (빌더에게 맡기는 것과 정한 것)

- **정한 것:** CodeMirror 의 `search({ top: true, createPanel })` 으로 패널 DOM 을 직접 만든다. 검색 엔진·결과 칠·명령(`findNext`, `findPrevious`, `replaceNext`, `replaceAll`, `closeSearchPanel`, `setSearchQuery`, `getSearchQuery`, `SearchQuery`)은 `@codemirror/search` 6.7 의 것을 그대로 쓴다. 새 검색 엔진을 만들지 않는다.
- **정한 것:** 새 패널은 `src/editor/` 아래 한 파일(예: `search-bar.ts`)에 둔다. 개수 세기는 DOM 없이 시험할 수 있는 순수 함수로 뺀다.
- **빌더에게 맡김:** 아이콘을 글자(`Aa`·`ab`·`.*`·↑·↓·⇄·×)로 할지 인라인 SVG 로 할지, 정확한 여백·크기. 단 시안의 비율과 「한 줄 띠」 인상을 지킨다.
- **정한 것:** 개수 세기를 언제 미루고 어디서 끊는지는 「동작 · 개수 세기」 대로다(최종 리뷰 I2 판정).

## 시험 (계획이 구체화)

- 단위: 개수 세기 함수 — 0개, 몇 개, 1000+ 상한, 시간 예산(주입한 시계로 넘기면 상한·찾은 개수), 조각으로 나눠 찾아도 한 번에 찾은 것과 같음, 지금 위치 계산(이진 탐색), 틀린 정규식.
- 단위: 대비 — 새 변수와 띠가 쓰는 색 짝의 대비를 다크·라이트 기본값으로 계산해 기준 이상인지.
- e2e: ⌘F(메뉴가 아니라 편집기 키라 `page.keyboard` 로 누를 수 있음)로 띠 열기, 고른 글이 입력칸에 들어감, Enter·⇧Enter 로 이동하며 「n / m」 이 바뀜, 옵션 토글, ⌥⌘F 로 바꾸기 줄, 바꾸기·모두 바꾸기와 ⌘Z 한 번 되돌리기, Esc 로 닫고 편집기 포커스, 결과 없음·틀린 정규식 문구, 한글 조합 중 Enter 가 이동하지 않음, 칸 둘에서 띠가 섞이지 않음.
