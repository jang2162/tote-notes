# tote-notes 테마 고르개 — 설치한 확장 테마 고르기 설계

2026-11-14 기능 묶음의 하나다. 사용자가 설계 확인 없이 진행하라고 해서(2026-11-14) 브리프의 결정은 **코디네이터의 판단**, 브리프가 비워 둔 세부는 **구현자의 판단**으로 표시한다. 둘 다 사용자가 읽고 바꿀 수 있다.

## 목적

사용자가 설치·활성한 확장의 테마는 레지스트리에 실리지만 그려지지 않았다. 코어 설계 「테마」 절과 설정 설계 「테마 고르개」 항목이 약속한 대로, 설정 화면 「모양 › 테마」 고르개에서 레지스트리의 테마를 하나 골라 그 테마로 그리게 한다.

## 하지 않는 것

- 라이트·다크 모양마다 테마를 따로 고르기(옛 `theme.light`·`theme.dark` 되살리기). 사용자가 2026-11-02 에 없앴다(코디네이터의 판단).
- 테마 마켓, 테마 편집(코디네이터의 판단).
- 고른 테마를 메뉴·단축키로 바꾸기. 고르개 하나뿐이다(구현자의 판단: 브리프에 없다).

## 동작 (사람이 보는 것)

### 고르개

설정 화면 「모양」 의 「테마」 묶음은 지금처럼 고르개(`<select>`, 칸 이름 「테마」) 하나다. 옵션은 위에서부터:

1. 「자동」·「라이트」·「다크」 — 지금과 같다(코디네이터의 판단).
2. 구분: `<optgroup label="테마">`. 그 안에 **레지스트리의 모든 테마**를 레지스트리 순서(우선순위 순서. 기본값 「사용자 확장 먼저」 면 사용자 확장의 테마가 앞)로, 이름(`label`)으로 보인다. 번들 Light+·Dark+ 도 들어간다(코디네이터의 판단).
   - 구분을 `<optgroup>` 으로 한 이유(구현자의 판단): `<hr>` 은 WebKit 의 `<select>` 안에서 그려지지 않거나 옵션으로 세어지지 않아 접근 이름이 없다. `<optgroup>` 은 macOS 팝업 메뉴에서 소제목과 구분으로 그려지고 보조 기술도 묶음으로 읽는다. 묶음 이름 「테마」 는 고르개 이름과 같지만 위 셋(모드)과 아래(테마 하나)를 가르는 데는 충분하다. 버린 대안: 「설치한 테마」(번들 테마도 들어 있어 틀린 말이다), 이름 없는 묶음(WebKit 이 빈 소제목 줄을 그린다).
   - 레지스트리 순서를 그대로 쓰는 이유(구현자의 판단): 같은 순서를 확장 목록·언어 결정이 이미 쓰고, 이름순으로 바꾸면 번들 둘이 사용자 테마 사이에 끼어 찾기 어렵다.
3. 같은 이름이 둘 이상이면 그 옵션들 모두 뒤에 확장 이름을 괄호로 붙인다: 「Night (Night Theme)」. 확장 이름은 확장 목록에 보이는 이름(`displayName`)이다(코디네이터의 판단: 괄호, 구현자의 판단: 둘 다 붙인다 — 하나만 붙이면 붙지 않은 쪽이 어느 확장 것인지 여전히 모른다).
4. 고른 테마가 레지스트리에 없으면(확장을 지움·끔·이름이 바뀜) 묶음 맨 끝에 「<이름> (찾을 수 없음, 지금은 자동)」 옵션이 하나 생기고 그것이 선택돼 보인다. 이 옵션은 끌 수 없지만(`disabled`) 선택된 채 보인다. 다른 옵션을 고르면 사라진다(구현자의 판단: 문구. 「지금은 자동」 은 화면이 지금 무엇으로 그려지는지를 말한다).

### 그리기

- 테마를 고르면 **OS 모양과 상관없이 언제나 그 테마로** 그린다(코디네이터의 판단). 테마가 주지 않은 CSS 변수와 페이지의 `color-scheme` 은 테마 종류(`themeKind`)를 따른다 — 코어 설계 「테마」 절의 규칙 그대로.
- 「자동·라이트·다크」 는 지금과 똑같다(번들 기본 테마).
- 고른 테마가 레지스트리에 없으면 **자동처럼** 그린다(OS 모양의 번들 기본 테마). 설정 값은 지우지 않는다 — 확장을 다시 켜면(다시 설치하면) 그 테마로 돌아온다(코디네이터의 판단).
- 고른 테마의 파일을 읽지 못하면 지금과 같이 기본 변수로 그린다(코어 설계 「오류 처리」).
- 편집기 하이라이트(`tokenColors`)와 열린 뷰어(마크다운 미리보기·미디어 뷰어)도 따라 바뀐다. 뷰어는 이미 테마가 바뀔 때마다 변수를 받는다(`ThemeManager.onChange` → `Pane.setViewerTheme` → 뷰어 메시지 `theme`). 이 기능이 그 길을 바꾸지 않는다.
- 모든 창에 바로 적용된다(기존 `tote://config` 경로).

### 네이티브 모양

앱의 네이티브 모양(창 크롬·메뉴·대화상자·스크롤 막대, 웹뷰의 `prefers-color-scheme`)은 고른 테마의 **종류**를 따른다(코디네이터의 판단). Rust 가 종류를 정한다(`native_theme`, `src-tauri/src/app/appearance.rs`):

- 고른 테마가 레지스트리에 있으면 매니페스트의 `uiTheme`(`vs`·`hc-light` 는 라이트, `vs-dark`·`hc-black` 은 다크), 모르는 값이면 테마 파일 맨 위의 `type`(`light`·`hcLight`·`dark`·`hc`). 둘 다 모르면 `None`(시스템) — 프런트엔드도 그때는 OS 모양으로 칠한다(`themeKind` 의 마지막 대체가 OS 모양이므로 둘이 맞는다).
- 레지스트리에 없으면 자동과 같이 `None`.
- Rust 는 테마 파일의 `include` 를 따라가지 않는다(구현자의 판단). 그래서 `uiTheme` 을 모르는 값으로 적고 `type` 을 포함된 파일에만 둔 테마는 네이티브 모양이 시스템을 따르고 페이지는 포함된 `type` 을 따라 둘이 갈릴 수 있다. 매니페스트가 `uiTheme` 을 빠뜨리면 tote 는 `vs-dark` 로 읽으므로(`default_ui_theme`) 이 경우는 작성자가 모르는 값을 적었을 때뿐이다.
- 거는 때: 앱이 뜰 때(창을 열기 전), 그리고 설정이나 확장 집합이 바뀌어 모든 창에 `tote://config` 를 알릴 때마다(`broadcast_config`) — 확장을 끄거나 지우거나 다시 켜면 고른 테마가 레지스트리에서 빠지거나 돌아오기 때문이다(구현자의 판단: 알림 자리 한 곳에 두면 레지스트리를 바꾸는 새 명령도 저절로 따른다. 같은 값을 다시 거는 것은 모양을 바꾸지 않는다).

## 데이터·저장

- settings.json `theme.mode` 는 문자열 `"auto"`·`"light"`·`"dark"`, 또는 테마를 가리키는 객체 `{"extension": "<확장 id>", "label": "<테마 이름>"}` 이다(구현자의 판단). 옛 `theme.light`·`theme.dark` 가 쓰던 꼴(`ThemeRef`)과 같다.
  - 확장 id 와 이름으로 가리키는 이유: 매니페스트의 테마에는 안정된 id 가 없고(tote 는 VS Code 의 선택 필드 `id` 를 읽지 않는다), 레지스트리의 순번은 확장을 켜고 끌 때 바뀐다. 테마 이름이 바뀌면 찾지 못해 자동으로 그리고 값은 남는다 — 브리프가 요구한 「깨지지 않음」 이다.
  - 같은 확장에 같은 이름의 테마가 둘이면 레지스트리에서 앞의 것이다.
  - 버린 대안: `"theme:<id>/<label>"` 같은 한 문자열. 이름에 `/` 가 들어가면 갈라 읽을 수 없고, 옛 슬롯 값과 꼴이 달라진다.
- **패치:** 기존 `themeMode` 가 그대로 객체도 받는다(구현자의 판단: 고르개 하나에 패치 하나. 새 이름을 만들면 「모드 패치와 테마 패치가 함께 오면 무엇이 이기나」 를 정해야 한다). 꼴이 틀린 값(모르는 문자열, `extension`·`label` 중 하나가 없거나 문자열이 아닌 객체)은 거절한다. 레지스트리에 있는지는 보지 않는다 — 없으면 자동으로 그릴 뿐이고, 고르개는 레지스트리의 테마만 내놓는다.
- **손으로 고친 settings.json 의 잘못된 값**은 지금처럼 그 값만 자동으로 돌아가고 나머지 설정은 남는다(`lenient`).
- **옛 판(이 기능 전의 판)이 객체 값을 읽으면:** `theme.mode` 를 `ThemeMode` 열거로 읽다 실패해 `lenient` 로 자동이 된다. 나머지 설정은 남는다. 옛 판이 그 뒤 설정을 하나라도 저장하면 `theme.mode` 는 `"auto"` 로 덮인다 — 고른 테마는 잊히고 새 판으로 돌아와도 자동이다. 앱이 깨지지는 않는다. 옛 판 코드에서 확인했다(`ThemeSettings::mode` 의 `deserialize_with = "lenient"`, 그리고 옛 시험 `theme_mode_is_auto_by_default_and_survives_a_bad_value` 가 숫자 `1` 로 같은 길을 본다).
- 세션·창 상태에는 아무것도 더하지 않는다.

## 단축키·메뉴

없다. 새 단축키·메뉴 항목이 없으므로 기존 키와 겹칠 것도 없다.

## 시험

- 단위(vitest, `src/theme/manager.test.ts`)
  - 고른 확장 테마를 OS 모양과 상관없이 그리고, 종류가 테마의 것이다.
  - 고른 테마가 레지스트리에 없으면 자동처럼 그리고 설정 값은 그대로다. 다시 실리면 돌아온다.
  - 「고르지 않으면 사용자 확장 테마는 그려지지 않는다」(기존 시험의 뜻을 고쳐 남김).
- 단위(vitest, `src/ui/theme-options.test.ts`): 옵션 목록 — 모드 셋, 묶음, 같은 이름의 괄호, 찾을 수 없는 테마, 값의 왕복.
- Rust(`appdata.rs`): `theme.mode` 객체 읽기·쓰기, 꼴이 틀린 객체는 자동, 패치 객체 적용과 거절.
- Rust(`app/appearance.rs`): 고른 테마의 종류가 네이티브 모양이 된다(`uiTheme`, 모르는 `uiTheme` 이면 파일 `type`), 레지스트리에 없으면 `None`. 테마 파일의 `type` 은 설치된 확장 폴더에서 읽는다 — JSONC, `type` 없음, 깨진 파일, 없는 파일, `include` 는 따라가지 않음(`a_theme_files_type_is_read_from_its_installed_extension`, 2026-11-14 후속).
- e2e(`tests/e2e/settings.spec.ts`): 확장 테마를 고르면 그 색이 그려지고 OS 모양을 바꿔도 그대로다. 확장을 끄면 자동으로 그리고 값은 남으며 고르개에 「찾을 수 없음」 이 보인다. 다시 켜면 돌아온다. 열린 마크다운 미리보기가 새 테마 변수를 받는다. 같은 이름 둘의 괄호는 e2e 가 아니라 위 vitest(「names the extension after each theme whose name another one has too」)가 본다(2026-11-14 후속에서 고친 문장).
- e2e 는 네이티브 모양을 보지 못한다(가짜 백엔드에 없다). 실기기 확인은 보고서의 「사람 확인」 표.
