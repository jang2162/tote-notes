# tote-notes 이미지 붙여넣기·끌어 놓기 설계

2026-11-14. 2026-11-13 점검 끝에 추천된 기능 묶음 가운데 하나다. 사용자가 설계 확인 없이 바로 진행하라고 했으므로(2026-11-14) 동작은 **코디네이터의 판단**(작업 브리프)이고, 브리프가 비워 둔 세부는 **구현자의 판단**이다. 결정마다 둘 중 어느 쪽인지 붙인다.

## 목적

마크다운 메모에 그림을 넣으려면 지금은 Finder 에서 파일을 워크스페이스 폴더로 옮기고 `![](이름)` 을 손으로 쳐야 한다. 스크린숏을 ⌘V 로 붙이거나 Finder 에서 그림 파일을 편집기에 끌어 놓으면 그 일을 한 번에 하게 한다.

## 동작 (사람이 보는 것)

### 대상

- **마크다운 메모 탭의 편집기에서만** 동작한다(코디네이터의 판단). 마크다운 메모란 메모 탭(외부 파일 탭·휴지통 탭이 아니다)이면서 그 탭의 언어가 Markdown 인 것이다 — 사람이 상태 표시줄에서 고른 언어가 있으면 그것, 없으면 파일 이름(`.md`·`.markdown`)으로 정한다(코어 설계 「편집기」 의 언어 규칙과 같다, 구현자의 판단).
- 외부 파일 탭·다른 언어 메모·읽기 전용 탭(휴지통)·미리보기로 보고 있는 탭에서는 지금 동작 그대로다 — 붙여넣기는 텍스트만, 끌어 놓기는 외부 탭으로 열기(코디네이터의 판단).

### 붙여넣기(⌘V)

- 클립보드에 **텍스트가 없고** 이미지(`image/png`·`image/jpeg`·`image/gif`·`image/webp`)가 있으면 그 이미지를 워크스페이스 루트에 파일로 저장하고 **커서 자리에** `![](<파일 이름>)` 을 넣는다(코디네이터의 판단).
  - 「텍스트」 는 CodeMirror 가 붙여넣는 것과 같다 — `text/plain`, 그것이 비었으면 `text/uri-list`(구현자의 판단: 편집기가 텍스트를 붙일 수 있는 클립보드는 언제나 텍스트를 붙인다).
- **텍스트와 이미지가 함께 있으면 텍스트를 붙이고 이미지는 무시한다**(코디네이터의 판단). 브라우저에서 그림과 글을 함께 복사한 것이 그렇다. 이미지만 따로 붙이는 길(⌥⌘V 등)은 이 묶음에 넣지 않는다.
- 선택한 글이 있으면 링크가 그 글을 바꾼다(보통 붙여넣기와 같다). 커서가 여럿이면 주 커서 자리 하나에만 넣는다(구현자의 판단: 이미지 파일은 하나라 링크도 하나다).
- 파일 이름은 `<메모 이름> 이미지.<확장자>` 다. 메모 이름은 메모 파일 이름에서 확장자를 뗀 것이다(`회의 준비.md` → `회의 준비 이미지.png`). 이름이 겹치면 ` 2`, ` 3` … 을 붙인다(메모 이름의 겹침 규칙 `free_name` 과 같다). 확장자는 MIME 에 맞춘다: `png`·`jpg`·`gif`·`webp`(코디네이터의 판단, `image/jpeg` 의 `jpg` 는 구현자의 판단: macOS 스크린숏·카메라 앱이 쓰는 꼴).
- macOS WKWebView 가 클립보드의 이미지를 어느 MIME 으로 내주는지는 실기기에서만 보인다(스크린숏 ⌘⌃⇧4 는 TIFF 를 PNG 로 내주는 것으로 알려져 있다). 위 넷이 아닌 MIME 만 있으면 아무 일도 없다. 「사람 확인」.

### 끌어 놓기

- Finder 에서 이미지 파일(`png`·`jpg`·`jpeg`·`gif`·`webp`·`svg` — 확장자로, 대소문자 무시)을 **마크다운 메모의 편집기 위에** 놓으면, 그 파일을 워크스페이스 루트로 **복사**하고(원본은 그대로) 놓은 자리에 링크를 넣는다(코디네이터의 판단).
  - 「놓은 자리」 는 포인터 아래 글자 사이다. 그 자리를 글에서 찾지 못하면(편집기의 빈 아래쪽 등) 커서 자리다(구현자의 판단).
  - 복사한 파일의 이름은 원래 이름이고, 겹치면 ` 2` … 을 붙인다(가져오기와 같다, 구현자의 판단).
- **여러 개를 놓으면 줄마다 링크 하나씩**, Finder 가 넘긴 순서대로 넣는다(코디네이터의 판단).
- **이미지가 아닌 파일, 편집기 밖에 놓은 것은 지금처럼 외부 탭으로 연다**(코디네이터의 판단). 이미지와 다른 파일을 섞어 편집기에 놓으면 이미지는 링크로, 나머지는 외부 탭으로 간다(구현자의 판단).
- **워크스페이스 안의 파일을 놓으면 복사하지 않고 링크만 넣는다**(코디네이터의 판단). 「안」 은 워크스페이스 루트 **바로 아래**의 파일이다 — 워크스페이스는 평평하고 미리보기가 같은 폴더의 그림만 읽으므로, 하위 폴더(`.trash/` 등)의 파일은 밖의 파일처럼 복사한다(구현자의 판단). 경로 비교는 백엔드가 실제 경로(`canonicalize`)로 한다.
- 놓는 동안 편집기에 놓을 자리 표시(드롭 커서)는 나오지 않는다. 파일 끌기는 네이티브 창(wry)이 받아서 웹 페이지에는 끌기 이벤트가 오지 않기 때문이다(아래 「끌어 놓기의 길」).

### 링크의 꼴

- `![](이름)` — 대체 글(alt)은 비운다(구현자의 판단: 파일 이름이 이미 뜻을 말하고, 비워 두면 사람이 바로 채울 수 있다).
- 이름에 공백·괄호가 있으면 `![](<이름>)` 으로 감싼다(CommonMark 의 꺾쇠 주소). `%`·`<`·`>` 는 `%25`·`%3C`·`%3E` 로 쓴다(구현자의 판단: 꺾쇠 안에 쓸 수 없는 글자와, 미리보기가 퍼센트 인코딩을 풀 때 다른 글자로 읽힐 글자다). 한글은 그대로 둔다 — 사람이 읽는 글이다.
- 링크를 넣은 뒤 커서는 마지막 링크 바로 뒤에 둔다. 넣기는 실행 취소 한 단계다(구현자의 판단).

### 미리보기

- 넣은 링크는 미리보기에서 이미지로 보인다(같은 폴더의 그림 — 코어 설계 「마크다운 미리보기」).
- **미리보기 뷰어가 이미지 주소의 퍼센트 인코딩을 풀어서 찾는다**(구현자의 판단). 뷰어의 `marked` 는 이미지 주소를 `encodeURI` 한 꼴로 내놓는다 — `<회의 준비 이미지.png>` 는 `%ED%9A%8C…%20…png` 가 된다. 이것을 그대로 `resolveRelative` 에 넘기면 그런 이름의 파일이 없어 「찾을 수 없음」 이었다. 이 묶음 전부터 한글·공백 이름의 그림이 미리보기에 보이지 않던 결함이고, 이 기능의 링크는 언제나 한글을 담으므로 같이 고친다. 푼 이름도 백엔드가 같은 폴더의 한 조각 이름만 받는다(`resolve_relative`)는 것은 그대로다.

### 크기 제한

- 이미지 하나가 **20MB(20 × 1024 × 1024 바이트)를 넘으면 넣지 않고** 상태 표시줄에 한 줄 띄운다(코디네이터의 판단). 붙여넣기는 「20MB 가 넘는 이미지는 넣을 수 없습니다」, 끌어 놓기는 같은 문구 뒤에 `: <파일 이름>`(구현자의 판단). 여럿을 놓았으면 넘지 않는 것은 그대로 넣는다.
- 붙여넣기는 페이지가 바이트를 보내기 전에 보고 거절한다. 백엔드도 같은 한도로 거절한다(`too-large`) — 두 길 모두 백엔드가 마지막 문이다(구현자의 판단).

### 실패

- 저장·복사가 실패하면(디스크, 권한, 읽을 수 없는 원본) 링크를 넣지 않고 상태 표시줄에 오류를 띄운다(구현자의 판단, 앱의 다른 백엔드 오류와 같은 길 `report`).
- 저장을 기다리는 사이에 글이 바뀌어도 링크는 처음 자리(그 사이의 편집으로 옮겨진 자리)에 들어간다. 그 사이에 같은 칸에서 다른 탭으로 바꿨으면 링크는 원래 탭의 글에 들어간다(보이지 않는 탭의 상태를 바꾼다). 그 사이에 탭을 닫았으면 이미지 파일만 남고 링크는 넣지 않는다(구현자의 판단).

### 메모 목록과 이미지

- 새 이미지 파일은 메모 목록에 미디어로 나타난다(지금 규칙, 코디네이터의 판단). `svg` 는 지금 목록 규칙에서 미디어가 아니라 텍스트 메모로 나온다(`kind_for` — 이 묶음은 바꾸지 않는다).
- **메모와 이미지를 묶는 관계는 없다.** 메모를 지우거나 휴지통으로 옮겨도 이미지는 남고, 이미지를 지워도 메모의 링크는 남는다(미리보기에서 「찾을 수 없음」, 코디네이터의 판단).
- 백업은 지금처럼 바이너리 파일을 뺀다(코어 설계 「백업」) — 붙인 PNG·JPEG·GIF·WebP 는 스냅샷에 들어가지 않는다. `svg` 는 텍스트라 들어간다.

### 단축키·메뉴·설정

없다. 새 메뉴 항목·단축키·settings.json 키를 더하지 않는다. ⌘V 는 지금의 「편집 › 붙여넣기」 그대로이고, 웹 페이지가 받는 `paste` 이벤트에서 판단한다.

## 데이터·저장

### 백엔드 명령 (구현자의 판단)

| 명령           | 받는 것                                        | 돌려주는 것                                   |
| -------------- | ---------------------------------------------- | --------------------------------------------- |
| `save_image`   | 바이트(바이너리 IPC 본문) + `x-file-name` 헤더 | 쓴 메모 정보(`MemoInfo`, 실제 이름은 `file`)  |
| `import_image` | 놓은 파일의 절대 경로                          | `{ file, memo? }` — 복사했으면 `memo` 가 있다 |

- **둘 다 이름은 한 조각만 받는다**: 비어 있지 않고, `/`·`\`·`:` 등 금지 글자가 없고, 점으로 시작하지 않는 이름(`is_valid_file_name`). 아니면 `invalid-name`. 이미지 확장자(`png`·`jpg`·`jpeg`·`gif`·`webp`·`svg`)가 아니어도 `invalid-name` 이다. 원하는 이름이 겹치면 ` 2` … 로 바꿔 쓰고, 쓴 이름을 돌려준다.
- **원자적 쓰기:** `save_image` 는 임시 파일에 쓰고 rename 한다(`atomic_write_seen`, 메모 저장과 같다). `import_image` 도 원본을 메모리로 읽어(20MB 한도라 버퍼가 작다) `save_image` 와 같은 길(`add_memo` → `atomic_write_seen`)로 쓴다 — 가져오기의 `copy_in`(파일에서 파일로 흘려 복사)을 쓰지 않는다. `copy_in` 이 쓴 것은 텍스트만 자기 쓰기로 기록되어(`came_in`), 이미지를 그 길로 쓰면 감시기가 다른 앱의 변경으로 알린다(2026-11-14 후속에서 코드에 맞춰 고친 문장).
- **자기 쓰기로 기록한다:** 쓴 파일은 감시기의 자기 쓰기 기록(`Workspace::held`·inode)에 들어가, 감시기가 그 파일의 생성을 「다른 앱이 만든 파일」 로 알리지 않는다. 메모 색인에는 `autoTitle: false` 로 들어간다(가져온 파일과 같다).
- **크기:** 20MB 를 넘는 바이트·원본 파일은 쓰기 전에 거절한다(`too-large`). 원본은 연 파일의 크기로 본다.
- 바이트는 바이너리 IPC(`Uint8Array` 본문)로 가고 이름은 퍼센트 인코딩한 헤더로 간다(`import_memo` 와 같은 꼴).
- 쓴 뒤 같은 워크스페이스의 다른 창에 메모 목록 변경을 알린다(`tote://memos`). 워크스페이스 안의 파일을 놓아 복사하지 않은 경우는 알리지 않는다.

### 끌어 놓기의 길 (구현자의 판단)

- Tauri 의 파일 끌기(`dragDropEnabled`, 기본 켜짐)에서 wry 는 놓기를 네이티브 창에서 받고 웹 페이지에는 넘기지 않는다(`perform_drag_operation` 이 처리기의 `true` 를 보고 WKWebView 를 부르지 않는다). 그래서 웹 페이지의 `drop` 이벤트·`DataTransfer` 에는 Finder 파일이 오지 않고, 오더라도 경로가 없어 「워크스페이스 안의 파일」 을 가를 수 없다.
- 그러므로 Tauri 가 보내는 놓기 알림(`onDragDropEvent` 의 경로 목록과 `position`)을 쓴다. `position` 은 macOS 에서 웹뷰 왼쪽 위 기준 포인트(= 확대 1 의 CSS px)다 — wry 가 `draggingLocation` 을 그대로 넘기고 Tauri 가 바꾸지 않는다. 다른 플랫폼은 물리 픽셀일 수 있다(macOS 먼저, 코어 설계 「플랫폼과 스택」).
- 앱은 그 좌표 아래 요소의 편집기(`.cm-editor`)를 찾고, 그 편집기의 지금 탭이 이미지를 받으면(위 「대상」) 이미지 경로를 가져가고 나머지를 지금 길(외부 탭으로 열기)로 넘긴다. 편집기가 가져간 경로는 외부 탭 길로 가지 않는다.
- e2e 는 가짜 백엔드의 `dropFiles(paths, at)` 로 같은 알림을 흉내 낸다. 브리프의 「Playwright 의 `DataTransfer` 흉내」 대신 이것을 쓴 이유는 위와 같다 — 실제 앱이 지나지 않는 길을 시험하게 된다.

## 하지 않는 것

이미지 하위 폴더(`assets/`), 이미지 크기 줄이기·변환, 외부 파일 탭·다른 언어 메모에 붙여넣기, 원격 이미지 내려받기, 이미지와 메모의 묶음 관리(지울 때 함께 지우기) — 코디네이터의 판단. 이미지만 따로 붙이는 단축키(⌥⌘V), 놓는 동안의 드롭 커서, 커서 여럿에 같은 링크 넣기 — 구현자의 판단.

## 시험

- **저장 응답을 기다리는 사이의 한글 조합 (2026-11-14 후속, 재현되지 않음).** 붙여넣은 뒤 저장 응답 전에 한글을 조합하기 시작하면 링크가 조합 자리에 끼어드는가를 e2e 로 재현해 보았다: `saveImage` 를 붙잡고, `tests/e2e/tear-off.spec.ts` 의 조합 시험과 같은 합성 이벤트(`compositionstart` → `insertCompositionText` ㄱ)로 조합을 연 채 저장을 풀고, 조합을 ㄱ→가로 이어 `compositionend` 까지. 커서가 붙여넣은 자리에 있을 때(「앞|뒤」)와 다른 자리(글 끝)에서 조합할 때 둘 다 링크는 붙여넣은 자리에 들어가고 조합한 글자는 온전했다(「앞![](<a 이미지.png>)가뒤」, 「앞![](<a 이미지.png>)뒤가」). 그래서 고치지 않았다. 다만 링크를 넣는 편집이 조합 중에도 커서를 링크 뒤로 옮긴다 — 합성 이벤트의 입력기는 그 커서를 따르지 않지만, 실제 입력기가 조합 중 커서가 옮겨질 때 글자를 일찍 확정하거나 다음 자모를 새 커서 자리에 넣는지는 실기기에서만 보인다(「사람 확인」).
